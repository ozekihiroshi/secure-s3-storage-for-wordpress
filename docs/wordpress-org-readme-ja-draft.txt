短い説明：
WordPressに長期AWSアクセスキーを保存せず、データベースとアップロード済みメディアをAmazon S3へバックアップします。

== Description ==

= 初めてのバックアップ =

[導入ガイド](https://github.com/ozekihiroshi/secure-s3-storage-for-wordpress/blob/main/docs/getting-started-ja.md)に沿って、利用環境の確認、非公開のS3保存先の作成、AWSの権限設定、接続確認、初回データベースバックアップの順に進めます。IAMポリシー全文の例も掲載しています。WordPressへのAWSキー入力は不要です。

Ozeki Database Backup for S3は、WordPressのデータベースとアップロード済みメディアをAmazon S3へ安全にバックアップするためのプラグインです。

IAMロールを関連付けたAmazon EC2など、WordPressがAWS SDK for PHPの標準認証情報取得機能を利用できる環境を対象とします。AWSアクセスキーIDやシークレットアクセスキーをWordPressのデータベースに保存するための入力欄はありません。

現在の主な機能：

* WordPress管理画面からの手動データベースバックアップ。
* WP-Cronによる毎日のデータベースバックアップ。
* WP-CLIのデータベースバックアップコマンドと状態確認コマンド。
* SQLダンプのgzip圧縮。
* AWS SDK for PHPを使ったAmazon S3へのアップロード。
* 利用可能な場合はmysqldumpまたはmariadb-dumpを使用。
* ダンプ用プログラムや外部プロセス実行が利用できない場合はPHP方式へ切替。
* 1以上の整数で指定できる保持件数。
* WordPress内に保存するバックアップ履歴。
* 一時的な試験ファイルを使ったS3接続確認。
* 無効化時のプラグインCronイベントの解除。
* 管理画面から開始するuploadsディレクトリの手動バックアップ。
* WordPress Cronによるメディア一覧・チェックサムの準備、マルチパートアップロード、検証。
* ファイルごとのSHA-256一覧とS3の最終完了マーカー。
* メディアの状態確認、処理実行、準備、開始、失敗した処理の明示的削除を行うWP-CLIコマンド。

= AWS認証 =

AWS SDK for PHPの標準認証情報取得機能を使用します。管理画面でAWSアクセスキーIDやシークレットアクセスキーの入力を求めず、長期認証情報を意図的にWordPressデータベースへ保存しません。

Amazon EC2では、インスタンスにIAMロールを関連付ける方法を推奨します。他の認証情報取得元も、サーバー環境によっては利用できます。WordPressが使用するAWSの認証主体には、設定したS3バケットとプレフィックスへの適切な権限が必要です。

= データベースのバックアップ =

データベースをSQLダンプとして書き出し、gzipで圧縮してS3へアップロードします。

gzipを展開した結果が元のSQLと一致することを確認し、SHA-256チェックサムを送信します。S3に保存したファイルのサイズとチェックサムも確認してから成功とします。新しい履歴には圧縮ファイルのSHA-256とS3の検証状態を記録します。古いバックアップを自動的に検証済みにはしません。S3の保存内容の検証は、データベースの復元試験とは異なります。

アップロード権限に加えて、オブジェクトのメタデータとチェックサムを読む権限が必要です。KMSを使う場合は暗号化関連の権限も確認してください。検証に失敗した場合、成功を条件とする保持削除は実行しません。失敗前にアップロード済みのファイルは、調査用としてS3に残る場合があります。データベースは単一オブジェクトとして保存し、マルチパート処理にはしません。

保存場所：

`<configured-prefix>/backups/database/YYYY/MM/DD/`

mysqldumpやmariadb-dumpが利用できる場合は優先して使用します。適切なプログラムやPHPからの外部プロセス実行が利用できない場合は、PHP方式で書き出します。

= メディアのバックアップ =

シングルサイトのWordPressで、現在のuploadsディレクトリ以下の通常ファイルを対象とします。データベースとは別の操作で、明示的な開始が必要です。

バックグラウンドで処理量を区切りながら、並べ替えたファイル一覧とSHA-256を準備します。ファイルを個別のS3オブジェクトとして保存し、一覧と保存済みオブジェクトを検証してから完了マーカーを作成します。大きいファイルにはマルチパートアップロードを使用します。

保存場所：

`<configured-prefix>/backups/media/<random-job-id>/`

管理画面から開始する前に、サーバー管理者がwp-config.phpでODBFS3_MEDIA_WORK_DIRを定義してください。WordPressのPHPユーザー所有・権限0700の既存の永続POSIXディレクトリを指定します。Webルート、wp-content、uploadsの外に置いてください。公開される場所や、処理中に削除される可能性がある一時ディレクトリは使用しません。

例：

`define('ODBFS3_MEDIA_WORK_DIR', '/private/persistent/wordpress-media-work');`

実行中はuploadsを変更しないでください。ファイルやディレクトリの追加・削除・名前変更・内容変更があると、安全のため処理が停止する場合があります。この版にはメディアの自動実行や保持削除はありません。失敗した処理は調査のうえ、その処理IDを指定してWP-CLIで明示的に削除してから次の処理を開始します。

この版には本番用のメディア復元コマンドはありません。S3の完了マーカーと一覧は、独立した復元と全ファイルのSHA-256検証に利用するためのものです。WordPress全体の復旧には、適切なデータベースのバックアップと、それに対応するメディアのバックアップが必要です。

= 自動データベースバックアップとWP-Cron =

自動バックアップはWP-Cronを使用します。WP-CronはWordPressへのリクエストで起動するため、指定時刻にアクセスがなければ遅れて実行される場合があります。

一定間隔での実行が重要な環境では、OSの定期実行からWordPress Cronを起動してください。

通常のWP-CLIの例：

`*/5 * * * * cd /path/to/wordpress && wp cron event run --due-now --quiet`

WP-CLIサービスを持つDocker Composeの例：

`*/5 * * * * cd /path/to/docker-project && docker compose run --rm wp-cli cron event run --due-now --quiet`

これらは例です。パス、ユーザー、コンテナ構成、実行権限は利用環境に合わせてください。

= 保持件数 =

保持削除を無効にするか、最新のデータベースバックアップを残す件数を1以上の整数で指定できます。対象は、設定したS3プレフィックス以下でプラグイン所定の命名形式に一致するデータベースバックアップだけです。

手動バックアップでは保持削除を行いません。自動バックアップとプラグインのWP-CLIバックアップコマンドでは、成功後に設定した保持方針を適用します。

0.4.1から、削除前に残すファイルを元のSHA-256メタデータとS3チェックサムで確認します。検証情報の欠落、不一致、確認権限の不足、一覧の取得不足があれば削除を停止します。メタデータがない旧バックアップでは、新しい検証可能なバックアップが必要件数揃うまで削除が延期される場合があります。バックアップの成功と保持削除の失敗は別々に記録します。

= アンインストール時の動作 =

無効化時には、データベースとメディアのCronイベントを解除します。設定・履歴・メディア処理状態は残ります。

アンインストール時には、WordPress内の通常の設定・バックアップ履歴・現在および過去のメディア処理情報を削除します。

S3に保存されたデータベースやメディアのバックアップは削除しません。非公開のメディア作業ディレクトリや、未把握の未完了マルチパートアップロードも自動削除しません。

Recovery Setの収集・観測・実行・予定判定・削除記録は残ります。外部登録した定期実行は別途停止し、手動で廃止する前に復旧の根拠となる記録を保全してください。この版には、これらの記録の自動エクスポートや最終削除はありません。

プラグインを削除しただけで遠隔地のバックアップまで消えないよう、意図してこの動作にしています。

== External Service ==

データベースとメディアのバックアップを保存・管理するため、AWS SDK for PHPを使ってAmazon Web ServicesのAmazon S3へ接続します。

データベースのバックアップ時に送信するもの：

* 設定したS3バケット名。
* 設定したプレフィックスと生成した保存キー。
* gzip圧縮したSQLデータベースバックアップ。

メディアのバックアップ時に送信するもの：

* 設定したS3バケット名。
* 設定したプレフィックスと生成したメディア保存キー。
* WordPressのuploads内のファイル。
* 相対パス、サイズ、SHA-256、保存先対応表を含む生成済み一覧。
* すべてのメディアと一覧の検証後に生成する完了マーカー。

メディアのアップロードと検証では、マルチパートアップロードの作成・一覧取得・確認・完了・中止や、保存済みオブジェクトの確認を行う場合があります。特定の失敗した処理を明示的に削除する場合は、その記録にある未完了マルチパートだけを中止できます。完成したメディアバックアップを自動削除することはありません。

uploadsには個人情報、非公開情報、著作物などが含まれる場合があります。管理者が適切な保存先、アクセス方針、暗号化、保持方針、保存の法的根拠を選択してください。

データベースバックアップには、ユーザー情報、メールアドレス、投稿、コメント、プラグイン設定など、WordPressデータベース内の個人情報や機密情報が含まれる場合があります。

接続確認では、バケットへのアクセス確認、生成した試験文字列と時刻を含む一時ファイルの作成、読取りと内容確認、試験ファイルの削除を行います。

保持削除では、選択した方針に従い、設定したプレフィックス内のデータベースバックアップの一覧取得と削除を行う場合があります。

Amazon S3の利用にはAWSの規約とプライバシーポリシーが適用されます。

AWS Customer Agreement: https://aws.amazon.com/agreement/
AWS Privacy Notice: https://aws.amazon.com/privacy/
AWS Service Terms: https://aws.amazon.com/service-terms/

このプラグインは、作者に対するテレメトリー、分析、広告、無関係な追跡データの意図的な送信を行いません。

== Installation ==

設定を入力する前に[導入ガイド](https://github.com/ozekihiroshi/secure-s3-storage-for-wordpress/blob/main/docs/getting-started-ja.md)を確認してください。AWSコンソールの手順とIAMポリシー全文の例を掲載しています。設定画面にも利用者の表示言語に合ったガイドへのボタンがあります。

1. プラグインを導入・有効化します。
2. WordPressサーバーがAWS SDKの標準認証情報取得機能を使えることを確認します。
3. 利用するAWSの認証主体に、対象のS3バケットとプレフィックスへの権限を付与します。
4. 「設定 → Ozeki Database Backup for S3」を開きます。
5. AWSリージョン、S3バケット、必要に応じてS3プレフィックスを入力します。
6. 設定を保存します。
7. 「接続確認」でS3への書込み・読取り・削除を確認します。
8. 「今すぐバックアップ」で初回データベースバックアップを作成します。
9. 成功後、必要なら毎日の自動実行を有効にします。保持削除を有効にする前に、ガイドの追加権限の手順を確認してください。初回用ポリシーはバックアップ本体の削除を許可しません。
10. メディアを保存する場合、Web公開領域外にPHPユーザー所有・権限0700の永続POSIXディレクトリを作成します。
11. wp-config.phpのODBFS3_MEDIA_WORK_DIRにその絶対パスを指定します。
12. 設定画面で「メディアのバックアップを開始」を押します。成功または失敗が確定するまでuploadsを変更しないでください。

EC2では、長期アクセスキーをサーバーに保存するより、インスタンスへのIAMロールの関連付けを推奨します。

== Frequently Asked Questions ==

= AWSアクセスキーIDやシークレットアクセスキーを保存しますか？ =

長期キーの入力欄はなく、意図的にWordPressデータベースへ保存しません。認証にはAWS SDK for PHPの標準認証情報取得機能を使用します。

= EC2のIAMロールは必須ですか？ =

いいえ。EC2上では推奨しますが、AWS SDKの標準機能が対応する他の取得元も利用できる場合があります。

= データベースバックアップは暗号化されますか？ =

AWS SDKの接続を使ってS3へアップロードします。保存時の暗号化は保存先バケットとAWS設定によります。管理者が必要なセキュリティ・法令対応に合わせて設定してください。

= アンインストールするとS3のバックアップも削除されますか？ =

いいえ。S3のデータベースバックアップは意図して残します。

= 自動バックアップは指定時刻ちょうどに実行されますか？ =

必ずしもそうではありません。WP-CronはWordPressへのリクエストで起動します。より確実な間隔で実行するには、OSの定期実行から期限の来たWordPress Cronイベントを起動してください。

= mysqldumpが使えない場合はどうなりますか？ =

対応するダンププログラムや外部プロセス実行が利用できなければ、PHP方式へ切り替えられます。PHP方式はWordPressに定義済みの接続定数を使い、専用のDB接続を開きます。一貫したスナップショット用のトランザクションをWordPressの共有接続から分離します。HTTPリクエストやプラグイン設定から接続情報を受け取りません。

= 接続確認は何をしますか？ =

バケットへのアクセスを確認し、一時ファイルを書き込み、読み戻して内容を検証し、削除します。

= メディアバックアップには何が含まれますか？ =

シングルサイトの現在のuploads以下の通常ファイルです。データベース、テーマ、プラグイン、wp-config.php、その他のサイトファイルは含みません。対応するデータベースは別途バックアップしてください。

= メディアバックアップを復元できますか？ =

この版では復元機能を提供しません。完成したバックアップには検証済み一覧、個別ファイル、完了マーカーがあり、独立して検証する復元手順で使用できます。バックアップに依存する前に復元手順を試してください。

= メディアの自動実行や保持削除はできますか？ =

この版ではできません。明示的に開始し、データベースの毎日の自動実行や保持件数とは別に扱います。

== WP-CLI ==

データベースバックアップ：
`wp ozeki-database-backup-for-s3 backup`

設定と状態の表示：
`wp ozeki-database-backup-for-s3 status`

既存の非公開作業領域を使ってメディアの準備・アップロードを予約：
`wp ozeki-database-backup-for-s3 media enqueue /private/persistent/wordpress-media-work`

安全に表示できるメディア処理状態：
`wp ozeki-database-backup-for-s3 media status`

サーバーの定期実行などから、処理量を区切ったワーカーを1回実行：
`wp ozeki-database-backup-for-s3 media tick`

バックグラウンド一覧作成の上限を超えるディレクトリでは、WP-CLIで準備して開始：
`wp ozeki-database-backup-for-s3 media prepare /private/persistent/wordpress-media-work`
`wp ozeki-database-backup-for-s3 media start /private/persistent/wordpress-media-work/odbfs3-preparation-...`

特定の失敗した処理を調査した後、その記録にある未完了マルチパートと非公開作業領域だけを削除：
`wp ozeki-database-backup-for-s3 media cleanup <job-id> --yes`

= Recovery Sets（0.4.0で導入） =

「設定 → Recovery Sets」は、サイト内に保存されたセット、構成要素・マニフェストの検証、後続の観測、実行記録、削除記録の進捗を表示します。閲覧だけではセット作成、S3接続、復元試験、ファイル削除は行いません。通常のバックアップ履歴を自動的にセットへ変換することもありません。

管理者は予定判定の有効・停止、初回予定時刻（UTC）、間隔、開始・完了の猶予（秒）を明示的に保存できます。これは予定の判定だけを行い、実際のCronの開始・停止・予約変更は行いません。保存には確認、有効なnonce、現在の設定リビジョンが必要です。古いフォームは拒否するため再読み込みしてください。判定再開には未来の初回予定時刻が必要です。未完了の実行記録は残しますが、ワーカーが動作中である証明にはなりません。recovery-set executionとrecovery-set schedule-statusに--source-idと--format=jsonを指定すると、読取り専用JSONを取得できます。

以下のIDは32文字の小文字16進数に置き換えます。
`wp ozeki-database-backup-for-s3 recovery-set status <set-id> --format=json`
`wp ozeki-database-backup-for-s3 recovery-set latest --source-id=<source-id> --format=json`
`wp ozeki-database-backup-for-s3 recovery-set observations <set-id> --format=json`

終了コード0は読取り成功を示し、バックアップや復元の成功を意味しません。処理段階、完全性、索引・集計の完全性、観測の鮮度を確認してください。索引は100件を上限とし、不完全な結果は明示します。観測の有効期間の既定値は24時間です。画面を更新してもS3の再検証はしません。

Recovery SetのCronは、固定構成、排他制御アダプター、結果報告を指定してWordPressRecoverySchedule::registerで組み込む開発者向けの仕組みです。有効化や通常の毎日のDBバックアップ設定では起動しません。呼出し1回で1操作進むため、完了まで繰り返しが必要です。日付の区切りはUTCです。失敗、検証情報の欠落、構成変更があれば調査し、再試行を強制するために記録を削除しないでください。保守前に外部定期実行と該当の連携hookを停止してください。無効化は外部登録のRecovery Set定期実行を管理しません。

最初にローカル削除計画を確認：
`wp ozeki-database-backup-for-s3 recovery-set cleanup-plan <set-id> --workspace-parent=<private-parent> --format=json`

復旧用資料と計画を確認してから実行：
`wp ozeki-database-backup-for-s3 recovery-set cleanup <set-id> --workspace-parent=<private-parent> --confirm-set=<same-set-id> --format=json`

対象は完了済みのdatabase.sqlとdatabase.sql.gzの一時ファイルだけで、各1 GiBが上限です。排他制御下でハッシュを再確認し、削除進捗を記録します。検証記録、メディアのディレクトリ、S3オブジェクトは残ります。中断時は原因を確認し、記録を保全して同じIDと親ディレクトリで再開します。自動・再帰的削除や、現在のS3接続性の確認ではありません。

汎用のRecovery Set作成・復元コマンドや取得設定画面はありません。予定判定フォームは取得処理を設定しません。DBとメディアの対応は同一時点のスナップショットを保証せず、ローカル記録には独立した署名を付けません。組込み・停止・障害時の手順はリポジトリのdocs/recovery-operations.mdを参照してください。これらは0.4.0で導入した操作です。
