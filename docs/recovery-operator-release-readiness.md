# Recovery Set改善の公開前確認

2026-10-19。対象は`codex/recovery-operator-plan`。今回の確認はローカル実装・検証記録・文書の照合で、GitHubやWordPress.orgの公開状態の再調査ではない。ソース版0.3.0の改善を整理したもので、配布更新・本番適用はまだ行っていない。

2026-10-19、累積レビューと特定候補ZIPの新規導入・0.2.1/0.3.0更新・状態保持は合格。WP-CLIの配布時名前空間問題と同梱説明を修正した。累積レビューと候補ZIPの受入は[今回の記録](recovery-cumulative-review.md)および[検証集計](recovery-zip-validation.json)に追記する。下表の一般的な公開条件と、検証済みの特定ZIPの範囲を区別する。

## 現在の判定

2026-10-19の[単独製品としての棚卸し](backup-standalone-status-audit.md)で範囲を再確認した。通知・外部監視は必須実装から除外する。以下の「本番監視通知」「report停止」の記述は運用側の選択事項であり、Backup for S3の完成条件やResilienceへの依存を意味しない。製品側では起動・進捗・結果の記録と予定超過の読取り表示、利用者向け作成/復元入口、失敗後の再試行、履歴上限を優先する。

同じ候補ZIPの[実S3往復・隔離復元](recovery-zip-real-s3.md)もnative/PHP両方式で合格。Cron呼出し・取得観測・cleanup後の資産を試験bridgeで実S3へ保存し、再取得から復元した。製品src/vendorはZIPと一致。Version IDなし・バケット設定読取り不可のため、固定版/保持の検証とは区別する。本番ワーカー連続実行と長期運転は引き続き未検証。

その後、同じZIPで[WordPress実ワーカーの直接S3保存・隔離復元](recovery-direct-worker-s3.md)もnative/PHP各48/44項目に合格した。専用WordPressの登録hookから製品Pipeline/Publisherを直接S3へ接続し、manifest書換え・資産の再公開なしで復元した。この試験は明示hook起動で、自動wp-cron起動は下記の別試験で確認した。長期運転・本番適用は未検証。

さらに[通常アクセスからの自動WP-Cron試験](recovery-auto-cron-s3.md)で、native/PHPの直接S3保存、並行アクセス抑止、停止再開、完了状態保持を確認した。続く[無アクセス時の外部crond試験](recovery-external-cron-s3.md)ではPHP方式で予定起動・起動漏れ2枠・停止再開を確認した。どちらも短い試験スケジュールを明示登録した専用環境の結果で、本番スケジュール導入・本番監視通知・日次枠越え/複数日運転は残る。

読取りCLI、索引・観測、Cron接続基盤、限定cleanup、読取り管理画面は実装・専用試験済み。開発版としてレビューできる状態。一般利用者が画面だけでRecovery Setの日次作成から復元まで完結できる状態とは扱わない。

以前のソース本体有効化・実ブラウザ試験は合格しているが、最終配布ZIPの更新試験を代用しない。試験件数をbackend/PHP版/前提fixture間で合算しない。

## 製品側の未提供・制限

| 項目 | 現状と次の判断 |
| --- | --- |
| 一般向け作成入口 | create CLI・Cron有効化UI・完成した導入bootstrapは未提供。開発者用接続基盤として公開するか、一般利用者用入口を次版で作るかを明示 |
| 復元/再検証 | 一般向け復元CLI/UI、自動定期verify、認証付き跨ホスト観測配送は未提供 |
| 失敗後の運用 | failedの承認付きリセット・設定移行、観測runningからの実処理再開は未提供。台帳削除で代用しない |
| 索引の規模 | セット/観測の読取り上限100。ページング、履歴保存/エクスポート、上限到達時の運用が必要 |
| 容量管理 | cleanupは完了DB一時ファイル2種・各1GiBまで。mediaや証拠・台帳の自動整理、再帰容量集計、保存日数ルールは未提供 |
| 長時間/複数ホスト | 60秒リースは強制終了制御ではない。大規模ダンプ・共有filesystem・OSクラッシュの耐久性は追加検証対象 |
| 保護範囲 | DB/mediaの対応付けは同一時点性を保証しない。サイト全体・侵害下の改ざん耐性・独立署名・Object Lock保持は本改善の保証外 |

これらすべてを開発版ソース公開の前提にはしない。制限付き開発版として説明する範囲と、一般運用を推奨する前に実装/検証すべき範囲を分ける。0.3.0の正式配布完了は宣言しない。

## 試験基盤・環境のメモ

CUA/Node REPLの初期化エラー、内部Dockerのポート公開とループバック中継、購読者の正常遷移先に合わない試験待機条件、fixtureのwpdb参照不足は[ブラウザ受入記録](recovery-admin-browser.md)にある。製品欠陥の件数として集計しない。初回WordPress標準Cron登録とログインセッション更新も、Recovery Set画面の変更と混同しない。

Resilienceの72時間継続観測やその環境課題は別プロジェクトの判定。本製品のREADME整理・レビューを止める条件にしない。

## 共通部品と製品の関係

本改善は`codex/recovery-operator-plan`、共通PHP DB部品採用は`codex/shared-backup-core`の別変更。共通化のマージ、バージョン固定、同梱版一致、配布更新は今回行わない。将来統合する場合は、統合後のcommitで関連試験を再実行する。

Backup for S3はバックアップ/リストアに必要な資産と整合性・運用確認を改善する。Resilienceは侵害・保存元喪失後も復旧できる独立した保管/信頼/復元体制を対象にする。共有可能な低層処理があっても、どちらかのプラグインの自動インストールや必須依存を今回追加しない。
