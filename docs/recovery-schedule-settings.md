# 管理画面で予定判定を設定する（開発版）

Backup for S3単独のRecovery Set機能。予定判定だけを設定する。実Cronの有効化・停止・周期変更、バックアップ起動、通知、外部監視、共通部品変更は含まない。

## 操作手順

1. 管理者で「設定 → Recovery Sets」を開く。
2. 対象のSource IDを入力して「実行記録を表示」を押す。セット詳細から開く場合は、そのセットの保存元が対象になる。
3. 「予定判定の設定」で、表示されているSource IDが目的の保存元であることを確認する。
4. 「有効／停止」、初回予定、予定周期、起動・完了の猶予時間を入力する。初回予定は**UTC**。周期・猶予は**秒**で入力する。
5. 「予定判定のみを変更し、実Cronは変更しない」確認欄にチェックし、「予定判定の設定を保存」を押す。
6. 再表示された現在設定と判定を確認する。実Cronを止めたい場合は[別の停止手順](recovery-cron-entry.md)が必要。

現在の取得処理はUTC日次枠なので、通常は周期86400秒、初回予定UTC 00:00（日本時間09:00）に合わせる。起動600秒・完了7200秒は入力例で、サイトに適した保証値ではない。判定周期を変えても実際の取得周期は変わらない。

初期フォームは「停止」を選択し、初回予定に翌日のUTC 00:00を表示する。**保存するまで設定は作成しない**。有効にしたい場合は利用者が選択する。停止から再開する場合は、未来の初回予定へ変更する。古い初回予定のままの再開は拒否する。

周期は60〜31536000秒。猶予は0以上、完了の猶予は起動の猶予以上かつ周期未満。日時の存在しない日付、配列値、負数、小数などはサーバー側でも拒否する。ブラウザが秒を省略した日時は00秒として扱う。

## 保存の安全性

- manage_options権限とPOSTのみ。ログインしているだけでは保存できない。
- WordPress nonceを保存元ID・表示時の設定ハッシュに結び付ける。別の保存元や状態への差し替えは拒否する。
- 表示時の設定と現在の設定を比較し、さらに既存APIのCASで保存する。別画面・別の管理者が変更した古いフォームは上書きしない。
- 保存先は`odbfs3_expectation_<source-id>`だけ。実Cron、Collector、署名・復元観測、実行記録、workspaceに書き込まない。
- 既存設定が壊れている場合はフォームを出さず、壊れた証拠を自動削除しない。
- 表示のGETは読取り専用。設定の保存は専用フォームの明示POSTだけで、バックアップやcleanupの操作フォームではない。

保存を確認できない場合、既に保存されている可能性もあるため、無条件に再送せず画面を再読込みする。最新設定と入力値を確認してから操作する。内部例外や認証情報はエラー画面へ表示しない。

## 検証範囲

[検証集計](recovery-schedule-settings-validation.json)：専用WordPressで38項目合格。既存予定判定39項目はPHP 8.1/8.3で回帰確認し、追加ハンドラーのPHP 8.1構文も確認した。

既存管理画面37項目と実WP-CLIの実行記録JSONも回帰確認し、表示前後のDBとworkspaceが不変であることを確認した。これらの件数は重複するため合算しない。

専用WordPress/MariaDBと生成データで、描画したフォームのnonce・値を使う保存、登録済みadmin-postハンドラーからの保存とローカル遷移、権限・nonce・差し替え・古いフォーム・不正入力の拒否、停止・再開・周期/猶予変更を検証する。期待設定以外のoptionsとworkspaceが変わらないことを照合する。

再実行：`python3 tools/test-recovery-status-local.py --schedule-settings-only`（WSL/Docker、ローカルイメージが必要）。実WordPressのrender・ハンドラー試験であり、ブラウザクリックによる受入や配布ZIPの更新試験とは区別する。本番適用・実S3通信・公開は行っていない。
