# S3・IAMの準備から初回バックアップまで

[English](getting-started.md) · [製品説明](../README.md)

このガイドの到達点は、WordPressのデータベースをS3へ一度保存し、保存結果を確認することです。画像などのメディアは、その後に別途保存します。Resilienceの導入は不要です。

次回版の開発ソースでは、プロフィールの「言語」に合わせて設定画面と導入ガイドの案内が切り替わります。「サイトのデフォルト」ならサイトの言語を使います。公開済み0.4.2は従来の日英併記と英語のボタン名です。操作の順序は同じです。

進む順番は **環境確認 → S3作成 → IAM設定 → WordPress設定 → 接続確認 → 初回バックアップ** です。

## 1. 自分のサーバーで使えるか確認する

WordPress 5.9以上、PHP 8.1以上、AWSアカウントが必要です。AWSの保存・通信には利用料金がかかります。この例は同じAWSアカウント内のEC2とS3を使います。

| 用語 | この手順での意味 |
|---|---|
| EC2 | WordPressが動くAWSのサーバー |
| S3バケット | サーバーとは別にバックアップを置く保管場所 |
| リージョン | 保管場所の地域。東京は `ap-northeast-1` |
| prefix | バケットの中でサイトを区別する保存先名。例：`sites/my-site/` |
| IAMロール | サーバーがAWSへアクセスするときに使う権限の入れ物 |
| IAMポリシー | どの保管場所で何を許可するかを記した設定 |

**EC2で動いている場合**：AWSコンソールで対象サーバーを確認でき、S3とIAMを設定できる方が以下を進めます。WordPressの管理者権限だけではAWSの設定はできません。

**レンタルサーバーなどEC2以外の場合**：先に提供会社へ「PHPのAWS SDK標準認証でS3を利用できるか、どの認証方法を提供するか」を確認してください。このプラグインにはアクセスキー入力欄はありません。サーバー側の認証を用意できない場合は、この設定例だけでは使い始められません。

担当者へ依頼する場合は、このガイドを渡し「S3保存先、リージョン、prefix、PHPから使えるAWS認証を用意してください」と伝えます。認証情報を問い合わせや公開文書へ貼り付ける必要はありません。

## 2. S3に専用の保管場所を作る

1. AWSコンソールで **S3 → バケットを作成** を開き、汎用バケットを選びます。
2. リージョンを選びます。通常はWordPressのEC2と同じ地域から始めます。
3. 他と重複しない名前を入力します。例の `replace-with-your-bucket` はそのまま使わず、自分の名前に置き換えます。
4. **ACL無効（Bucket owner enforced）**、**パブリックアクセスをすべてブロック**を維持します。バックアップを公開する必要はありません。
5. デフォルト暗号化は **SSE-S3（Amazon S3マネージドキー）** を選びます。この例は独自KMSキーや別AWSアカウントを使う構成を対象にしていません。
6. バージョニングは必要に応じて有効にできます。有効の場合、通常の削除では旧版が残るので、保持件数だけでは保存容量は減りません。最初から自動削除・アーカイブ移行・Object Lockの保持期間を設定する必要はありません。既存バケットを使う場合は、既存の削除・暗号化・ロック設定を担当者に確認します。
7. バケットを作成し、次の3項目を控えます。prefixは自分で決めます。S3画面でフォルダーを作る操作は不要です。

| WordPressに入力する欄 | 記入例 |
|---|---|
| AWS Region | `ap-northeast-1` |
| S3 Bucket | 作成したバケット名のみ。`s3://`やURLは付けない |
| S3 Prefix | `sites/my-site/`（サイトごとに別の値） |

[AWS公式：バケット作成](https://docs.aws.amazon.com/AmazonS3/latest/userguide/create-bucket-overview.html)

## 3. WordPressのサーバーに権限を与える

AWSの **EC2 → インスタンス → WordPressのサーバー → セキュリティ** で、付いているIAMロールを確認します。

- **既存ロールがある**：他のサービスに使われている可能性があります。ロールを置換せず、共有範囲と既存権限を確認してから、製品専用ポリシーを追加します。共有ポリシーを上書きしません。
- **ロールがない**：**IAM → ロール → ロールを作成 → AWSのサービス → EC2** で、EC2用ロールを作ります。以下のポリシーを付けた後、EC2の **アクション → セキュリティ → IAMロールを変更** で関連付けます。

ポリシーの作成手順：

1. [初回保存用の完全なJSON](aws-first-backup-policy.json)を開き、GitHubの **Raw（未加工）** 表示から全文をコピーします。最初の `{` から最後の `}` までで、行番号や画面の説明文は含めません。
2. `replace-with-your-bucket`を**すべて**実際のバケット名へ、`sites/example-site/`を**すべて**決めたprefixへ置き換えます。末尾の `/` と、JSON側の `*` を残します。
3. **IAM → ロール → 対象ロール → 許可を追加 → インラインポリシーを作成 → JSON** に全文を貼り付けます。
4. バケット名とprefixを見直し、`OzekiBackupInitial`など用途の分かる名前で保存します。既に同じ製品専用ポリシーがある場合は、それを編集します。

このポリシーは、専用領域への保存・読取り・メディア分割転送と、接続確認用ファイルの削除を許可します。バックアップ本体の保持削除は許可しません。接続確認のため、バケット内の一覧権限は専用バケット全体に与えています。書込み・読取りはprefix内に限定しています。他の既存ポリシーで付いた権限を、この例が取り消すわけではありません。

EC2ロールはサーバーの他の処理からも使える場合があります。「プラグインごとの認証隔離」ではありません。WordPressへAWSの管理者権限を与える必要はありません。

[AWS公式：EC2へのロール関連付け](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/attach-iam-role.html)

## 4. WordPressに保存先を入力する

1. プラグインを導入・有効化し、**設定 → Ozeki Database Backup for S3** を開きます。
2. 控えた **AWSリージョン / S3バケット / S3プレフィックス** を入力します。アクセスキーの入力は不要です。
   入力欄の薄い文字は例であり、保存済みの値ではありません。自分のバケット名などを実際に入力してください。
3. **自動実行を「無効」**、**保持件数を0（削除無効）**にして、**変更を保存**を押します。
4. **接続確認** を押します。小さな試験ファイルをS3へ作成し、読み戻して削除します。
5. 接続成功の表示を確認します。失敗した場合は次の表で原因を解消してから進みます。

| 表示・症状 | 次に確認すること |
|---|---|
| 認証情報が見つからない | EC2ロールの関連付けと、WebのPHPからの認証。Dockerではホストだけの成功で判断せず、コンテナ側を担当者に確認してもらう |
| AccessDenied / 403 | バケット・prefixの置換漏れ、実際に使われたロール、既存の拒否設定。権限を一律に広げず、失敗した操作を確認する |
| バケットが見つからない・地域のエラー | バケット名とリージョン。403だけでは不存在とは断定できない |
| 読めるが接続確認に失敗する | 試験ファイルの書込み・削除権限、Object Lockなど既存の制限 |
| 接続が時間切れ | サーバーからS3へのHTTPS通信、DNS、ネットワーク制限 |

## 5. 最初のデータベースバックアップを確認する

1. 同じ画面の **今すぐバックアップ** を押し、完了表示を待ちます。
2. **最近のバックアップ**に今回の時刻、成功結果、S3の保存先、サイズが表示され、**検証**欄で保存内容の検証結果を確認できることを確かめます。
3. AWSコンソールでも、指定したバケットの `prefix/backups/database/` 以下に今回の `.sql.gz` があることを確認します。prefixは自分が入力した値です。
4. エラーの場合は繰り返し実行する前にメッセージを確認します。DB書出し・一時領域・容量のエラーはサーバー担当者へ伝えます。

ここまでで**DBの初回保存と保存内容の確認**が完了です。画像などはまだバックアップしていません。復元確認は本番を上書きせず、隔離環境で行います。

## 6. 初回成功後に設定するもの

- **日次バックアップ**：WP-Cronが動くことを確認してから有効にします。アクセスの少ないサイトではサーバー側の定期実行が必要です。
- **保持削除**：この初回用ポリシーのまま有効にしません。必要な保持数を決め、専用prefixの`backups/database/*`への`s3:DeleteObject`許可を製品専用ポリシーに追加します。バージョニングの旧版・Object Lockとの関係も確認します。手動の「今すぐバックアップ」では保持削除は動きません。
- **画像などのメディア**：サーバー担当者がWeb公開領域外に永続作業ディレクトリを作り、PHPユーザー所有・権限0700にして、`wp-config.php`で`ODBFS3_MEDIA_WORK_DIR`を指定します。その後、**メディアのバックアップを開始**を実行します。DBとは別の操作です。[詳細](../readme.txt)。

保存先の3項目と運用手順は、元サーバーを失っても見られる場所に控えてください。
