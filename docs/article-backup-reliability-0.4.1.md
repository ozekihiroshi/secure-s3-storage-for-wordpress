# バックアップの信頼性は、保存後の確認と世代管理で変わる

## Ozeki Database Backup for S3 0.4.1の実装と検証

> 編集・公開用原稿。作成日：2026-10-27 JST。対象バージョン：0.4.1。
> 製品0.4.1は公開済みですが、この原稿は未公開です。
> 実装の参照は原則として `v0.4.1` に固定しています。
> 公開前検証記録にある「未公開」は検証完了当時の状態です。公開結果は末尾の公開記録を参照してください。

WordPressのバックアップでは、SQLファイルを生成し、Amazon S3へ保存できれば安心だと考えがちです。しかし、ファイルが存在すること、保存された内容が元と一致すること、実際に復旧できることは、それぞれ異なる確認です。

Ozeki Database Backup for S3 0.4.1では、この違いを整理しながら、古いバックアップを削除する際の安全性を改善しました。

本製品は、WordPressのデータベースとアップロードされたメディアを、管理者が用意したS3バケットへ保全する独立したプラグインです。Ozeki WordPress Resilienceの導入は必要ありません。今回の変更にも、両製品の共通DB部品への切り替えは含まれていません。

修正範囲は小さいものの、既存バックアップの保護という点で重要な修正です。実際のデータ消失事故を確認したという意味ではありません。コード上で成立する危険を特定し、対象を絞った試験で修正を確認したものです。

## 「バックアップ成功」で確認していること

データベースのバックアップは、SQLの生成、gzip圧縮、S3保存という段階を進みます。それぞれの段階で、異なる種類の確認を行います。

SQL生成では、利用するダンプ方式に応じて、プロセスの終了状態や出力の有無、データ取得・ファイル書き込みなどの失敗を確認します。ただし、処理が正常終了し、空でないSQLが生成されたことだけで、SQLの意味的な正しさや、あらゆるDBオブジェクトの復元可能性まで証明できるわけではありません。

圧縮後には、gzipを展開して元のSQLのサイズ・SHA-256と照合します。CRCやデータの切断、余剰データなども検査します。これは、生成したSQLが圧縮の過程で損なわれていないかを確認する処理です。元のSQLに必要な情報がすべて含まれているかという問題は、別に残ります。

S3への保存時には、gzipのSHA-256を指定してアップロードし、その後のHEADリクエストで保存先のサイズとチェックサムを照合します。また、既存キーへの上書きを拒否する条件を付けて保存します。

ここで確認しているのは、保存処理後の時点におけるサイズとチェックサムの一致です。通常のDBバックアップ処理が、毎回S3から全データを取得し、別のデータベースへ復元しているわけではありません。

実装参照：[DBバックアップ処理][database-service]、[gzip検証][gzip-verifier]、[S3保存・取得][s3-storage]。

## 今回の中心は「残すバックアップ」の確認

0.4.1以前にも、アップロード直後の整合性確認はありました。今回追加したのは、後日の世代管理でも利用できる照合情報と、その確認処理です。

問題となるのは、S3にオブジェクトが残っていても、バックアップ処理としては検証を完了できていない場合です。

例えば、保持数を2世代に設定し、古い順に次の3件があるとします。

- A：正常に保存・確認できたバックアップ
- B：S3にオブジェクトはあるが、確認を完了できなかったバックアップ
- C：その後、正常に保存・確認できたバックアップ

新しさだけで2件を残すと、BとCが保持枠に入り、Aが削除される可能性があります。Bの処理が失敗した時点で世代削除を止めても、後日のCの成功をきっかけに削除が実行されれば、問題は残ります。

0.4.1では、新規DBバックアップのgzipのSHA-256をS3オブジェクトのメタデータにも保存します。そして、古い世代の削除候補を決める前に、残す予定の全世代について次を確認します。

- 一覧に記録されたサイズと、HEADで取得したサイズが一致すること
- 元のSHA-256がメタデータに存在すること
- S3から取得したSHA-256チェックサムが、その値と一致すること

1件でも確認できなければ、削除候補を返さず処理を止めます。新しいバックアップの保存に成功していても、世代整理に失敗した場合は、その二つを区別して報告します。

ただし、この照合も復元試験ではありません。また、以前の処理でエラーになったオブジェクトでも、保存自体が正常に完了しており、今回の照合に通れば保持枠に数えられます。その場合も、過去の失敗履歴を成功に書き換えることはありません。

実装・試験参照：[保持処理][retention]、[保持処理の回帰試験][retention-tests]。

## 削除対象と一覧取得にも条件を設ける

世代管理では、どのファイルを削除対象と見なすかも重要です。

従来の判定は、DBバックアップ用の保存領域にある、`db-`で始まり`.sql.gz`で終わる名前を広く対象にしていました。0.4.1では、日付の階層やファイル名の日付など、プラグインが生成するキー形式に判定を限定しました。従来形式のバックアップとの互換性は維持しています。

これは、似た名前で手動保存したファイルを対象にする危険を減らす変更です。ただし、同じ形式を使う別サイトのバックアップを識別する仕組みではありません。保存先のprefixは、サイトごとに分ける必要があります。

S3の一覧取得についても、次のページを示すトークンの欠落や繰り返し、対象キーの重複などを検出すると、削除計画を中止します。不完全な情報から削除対象を決めないための防御です。

これらの判定も[保持処理の実装][retention]と[回帰試験][retention-tests]で確認できます。

## メディアとRecovery Setの「完了」が示す範囲

メディアバックアップでは、対象ファイルの一覧であるインベントリと、ファイルの件数・サイズ・ハッシュなどを使って転送結果を確認します。対象は単一サイトのuploads配下であり、WordPress本体、テーマ、プラグイン、設定ファイルまで含むサイト全体のバックアップではありません。

また、列挙、ハッシュ計算、転送には時間がかかります。その間にファイルが更新される可能性があるため、uploads全体の完全な同時点スナップショットを提供するものでもありません。

Recovery Setは、DBやメディアの復旧資源と、その確認記録を関連付けます。必要な構成要素が揃っているか、途中の状態か、どの検査が行われたかを扱います。

ただし、「complete」はその構成に必要な資源と確認が揃ったという意味です。DBのみの構成ならメディアは含みません。DBとメディアが完全に同じ時点の状態であることや、サイト全体の復旧成功を意味するものでもありません。

過去の検証記録と、現在の保存状態も区別が必要です。保存済みの状態表示だけでは、その後S3から資源が削除されたことを検知できません。過去の確認に加え、必要に応じて現在の取得可能性を確認する必要があります。

実装参照：[メディア転送][media-upload]、[Recovery Setの収集][recovery-collector]、[状態判定][recovery-status]、[検証記録の要約][recovery-observation]。

## 0.4.1では何を試験したか

公開前の確認では、最終配布ZIPを固定し、そのZIPを使って試験しました。ソースコード上の試験結果だけで、配布物の確認を代用していません。

| 検証対象 | 結果 |
| --- | --- |
| 配布ZIPの保持処理の回帰試験 | 26項目成功 |
| 配布ZIPのDB整合性試験 | 47項目成功 |
| 新規導入・公開0.4.0からの更新 | 成功。配布ファイルの一致と設定・履歴・未完了状態などの保持を確認 |
| Plugin Check 2.1.0 | 新規・更新の両ケースでruntime checksを含めエラーなし |
| 実際のS3での保持処理 | 23項目成功 |

実S3試験には、専用の保存領域と合成したgzipデータを使用しました。正常な場合の古い世代の削除、メタデータ不足や不一致による削除停止、対象外ファイルの保護、独立したGETによる取得・照合、既存キーへの上書き拒否を確認しています。

この試験では、本番データベースをダンプして復元したわけではありません。SSE-KMS、Object Lock、大量の世代、外部からの並行削除、長期運転なども網羅していません。

導入・更新試験は、WordPress 7.1.3、PHP 8.3.33、MariaDB 11.8の環境で実施しました。実WordPressの更新処理、管理画面の描画、設定処理などを確認していますが、実ブラウザによる全画面操作の試験ではありません。

公開後には、GitHubから取得したZIPのSHA-256が検証済みZIPと一致することを確認しました。WordPress.orgではZIPが再生成されるためアーカイブ自体のハッシュは異なりますが、展開した全3,894ファイルが一致することを確認しました。[最終ZIPの検証報告][validation]と[公開記録][publication]を公開しています。

これらは記録された条件での結果です。試験項目数やPlugin Checkの成功だけで、あらゆる障害条件での安全性や復旧成功を証明したとは扱いません。

## 保証の境界と、更新後の運用

0.4.1で強化したのは、確認できないオブジェクトを根拠に古いバックアップを削除しないための判断です。

この仕組みは、データとメタデータを同じ権限で変更できる主体に対する改ざん防止や、独立した電子署名ではありません。照合後に外部から削除されることも防げません。将来の取得可能性や、すべての環境での復旧成功を保証するものではありません。

また、WP-Cronによる実行はサイトへのアクセスなどの条件に左右されます。本製品が、すべての未実行や長時間停止を外部から監視・通知するわけではありません。バックアップ履歴の確認と、必要に応じた外部Cronや監視は運用上の課題として残ります。

更新直後には、0.4.0以前のバックアップに新しいSHA-256メタデータがないため、世代削除が延期される場合があります。設定した保持数の新しい照合可能なバックアップが揃うまで、保存数が設定値を超えることがあります。この期間はS3容量と保持処理の警告を確認してください。古いオブジェクトに手動でメタデータを書き足す必要はありません。

バックアップの信頼性を説明するときは、「生成できた」「保存内容を照合した」「後日取得できた」「復元して動作を確認した」を分けて示すことが大切です。0.4.1は、そのうち保存整合性を世代管理の判断にも利用し、既存の復旧資源を保護するための限定的な改善です。
